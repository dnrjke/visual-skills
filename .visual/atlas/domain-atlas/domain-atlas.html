Domain

The visual-atlas product scans a repo, maps its domains, and renders a navigable tree of orientation pages and focused technical topics.

OwnsThe atlas block model, the atlas.domains.json domain/topic hierarchy, deterministic page paths and navigation, mechanical drafts, self-contained rendering, and completeness checks.
WhyA standing onboarding-to-reference map: system and domain pages orient the reader, while recursively nested topic pages explain mechanisms without overloading their parents. Mechanical scan handles inventory; a human authors the hierarchy and meaning.
Self-describingThe page you are reading is this domain. The very generator documented below produced it — the scanner drafted these cards, then a human enriched them.
The load-bearing idea
"Hybrid — the scanner does the inventory, the human writes the domains and the why."

scanInventory finds modules, imports, and exports; reconcile maintains domain coverage; buildPageTree derives stable recursive paths and navigation; and the draft builders emit system, domain, and topic skeletons. The scanner never reorganizes the authored hierarchy.

How a full scan runs

flow

A full scan reconciles domain coverage, derives the authored page tree, and emits system, domain, and topic drafts only when absent. Rendering then adds navigation from the tree rather than copying it into authored JSON. A single-domain refresh regenerates that domain's complete configured subtree.

the hub (draft builders)grouping confighuman step

Drift is reported, never applied — the human edits atlas.domains.json globs to resolve it.

CLI bin/atlas.ts

↑ back to cards

The single entry point has three modes. Full scan reconciles domain coverage, validates the configured page tree, emits missing system/domain/topic drafts, and renders every configured page. Single-domain regenerates the selected domain plus every nested topic beneath it. Render-only replays committed JSON with navigation and page identity derived from the adjacent config; when output differs from source, it carries that config into the output so the emitted checker remains usable.

writeDraftIfAbsent is the no-clobber guarantee for full scans; --force requests clean replacement. listDocJsons follows configuration order when a tree exists and recursively discovers standalone page JSON otherwise. renderFile handles atlas, domain, and topic documents and passes derived navigation into the shared assembler.

config + page tree src/atlas-config.ts + src/atlas-tree.ts

↑ back to cards

atlas.domains.json is the human-owned source of truth: each DomainConfig carries a slug, name, and globs for source ownership, while optional recursive topics describe the reader's conceptual page tree. firstGuessConfig seeds domains; reconcile refills each domain's modules while preserving authored purposes, topics, source groups, and reading paths.

atlas-tree.ts turns the authored hierarchy into deterministic page identities, safe nested output paths, breadcrumbs, parent/child relationships, owner-scoped reading paths, and related-page validation. Topic sources are labeled include/exclude glob groups: they may overlap and span folders because they identify evidence, not ownership. resolveTopicSources fingerprints at file granularity. Drift remains explicit: reconcile reports unassigned modules, stale paths, and empty domains without reorganizing pages.

scan + draft src/gather-atlas.ts

↑ back to cards

The hub of the full-scan flow. scanInventory lists modules from the srcRoots — each root is a directory to walk or a single file — keeping files whose extension is in the config's moduleExtensions (TS/JS when omitted) and skipping generated/test trees and co-located *.test/*.spec files. For each TS/JS module it records resolved in-repo import keys, exported names, and whether it is a tRPC router; other configured extensions are inventoried by path only, with no imports or exports. It also collects Prisma model names. aggregateDomainEdges rolls module→module imports up to cross-domain slug→slug edges (intra-domain edges dropped).

buildAtlasDraft emits the system map and uses configured domain purposes. buildDomainDraft keeps the legacy deep inventory for domains without child topics, but produces a smaller orientation landing with a collapsed implementation reference when children exist. buildTopicDraft creates a plain lead, structured flow and rule sections, and labeled file groups from resolved evidence. The scanner supplies structure and inventory, not the technical explanation.

block model src/atlas-blocks.ts

↑ back to cards

The type backbone covers system and domain blocks plus four topic-oriented blocks: topic-tldr, topic-flow, topic-rules, and implementation-reference. PageNavigation carries derived breadcrumbs, the expanded branch, parent/child/sibling/related links, reading paths, and structured search entries. TopicOpts supplies topic shape and direct-entry context to the shared shell.

Beyond the types it carries page-option shapes (AtlasOpts/DomainOpts), LAYER_DOTS (the layer → fill;stroke color table), and small helpers: collectAtlasDiagrams pulls every rendered diagram in document order, assertUniqueAtlasIds enforces unique block/component/diagram ids, and isAtlasChapter/atlasChapterLabel drive the numbered chapter nav.

render src/assemble-atlas.ts

↑ back to cards

assembleAtlas, assembleDomain, and assembleTopic share one self-contained app shell and block dispatcher. Topic pages render plain leads, ordered flows, guarantees/failure behavior, and closed implementation-reference drawers. With derived navigation, the shell adds breadcrumbs, the current branch, child cards, owner-scoped reading paths on system/domain landings, nearby-page links, and a compact embedded search index.

Search indexes structured titles, purposes, aliases, breadcrumbs, and source paths—not every prose token. atlas-navigation.js filters that embedded data locally and creates safe result elements. All page kinds retain the same diagram, example, responsive-shell, and theme behavior.

quality checks src/lint-atlas.ts

↑ back to cards

lintAtlas, lintDomain, and lintTopic enforce the structural floor for their page kinds. A domain with child topics is orientation-first. A topic needs a lead with inputs and outputs, at least two complete flow steps, a guarantee plus failure behavior, and described implementation evidence.

lintReadability measures authored visible prose while excluding diagram source, code HTML, and collapsed implementation-file details. It warns on project-history language, long paragraphs or cards, oversized pages, topics under roughly 180 words, and multiple independent flows.

Substance diagnostics remain editorial: a multi-stage topic without a diagram or worked trace and an algorithm without a concrete example both render with warnings. The author must improve the explanation from source rather than pad words.

The emitted checker keeps readability findings advisory while failing unsafe or contradictory page structure, domain inventory drift derived from live globs, broken links, stale derived counts, structured references outside a page's evidence, and untouched topic scaffolds.

Each topic fingerprint covers its own config and evidence plus immediate child summaries, so deeper descendants remain independently reviewable. Every configured topic must clear the content floor before any stamp write; later link and grounding defects block the selected page without making an unrelated legacy page impossible to refresh.

Data it owns

Atlas owns the page block model and the grouping config — the two contracts every atlas page is built from. The block types below are the shape of a page; AtlasConfig/atlas.domains.json is the human-owned grouping.

AtlasConfig · atlas.domains.jsonThe human-owned grouping: domains as slug/name/globs, with scanner-resolved modules. The one lever for which files form which domain.
atlas-tldr · domain-map · domain-indexThe atlas-page blocks: the 'Start here' lead, the all-domains map, and the grid of domain tiles.
domain-tldr · components · depth · owns · seamsThe domain-page blocks: the lead, the component cards, the in-depth sections, the data-owned table (this block), and the neighbor seams.
diagram-section · exampleShared chapter blocks usable on either page type: diagram-section (the atlas spine/map and a domain page's internal-arch) and example (a worked-example chapter, re-exported from core).
Inventory · ModuleInfo · DriftThe mechanical scan products: per-module imports/exports/router flags, Prisma models, and the reported config drift.

The block model lives in atlas-blocks.ts; domain/topic/source types live in atlas-config.ts, and atlas-tree.ts derives navigation and evidence. The scanner fills modules and draft skeletons; a human owns grouping, page hierarchy, purpose, and detail.
